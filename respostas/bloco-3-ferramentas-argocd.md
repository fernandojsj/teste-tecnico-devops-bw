*3.1  O ArgoCD ajuda em qual etapa do processo de GitOps? O que exatamente ele faz?*

O ArgoCD atua na etapa de entrega contínua (CD) dentro do fluxo de GitOps, mais especificamente na parte de reconciliação. Ele não participa do build nem dos testes da aplicação, isso é responsabilidade da ferramenta de CI. O que ele faz é monitorar continuamente um repositório Git onde está declarado o estado desejado da infra/aplicação, comparar esse estado com o que está realmente rodando no cluster, e aplicar automaticamente qualquer diferença encontrada, seja porque o Git mudou ou porque o cluster teve alguma alteração manual. Além disso, ele expõe essa comparação de forma visual, mostrando claramente o que está sincronizado e o que não está.

*3.2  Onde termina a responsabilidade de uma ferramenta de CI (ex.: GitHub Actions, GitLab CI, Jenkins) e onde começa a do ArgoCD? Dê um exemplo do “ponto de entrega” entre as duas.*

A responsabilidade de uma ferramenta de CI termina quando ela entrega um artefato pronto e publicado no registry, com uma tag imutável (geralmente o SHA do commit). A CI não escreve no repositório de manifests nem tem acesso ao cluster; quem atualiza a referência do artefato (a tag da imagem) no repositório Git de configuração é o time de DevOps, manualmente. É esse commit que o ArgoCD detecta pra aplicar a mudança no cluster. Ou seja, o CI nunca acessa o cluster diretamente, e o ArgoCD nunca builda ou testa código, cada um atua estritamente do seu lado.

Um exemplo real desse "ponto de entrega": no pipeline que usamos na Evolutix, o Jenkins roda a análise de código no SonarQube, que barra o pipeline caso o quality gate não seja atingido, executa os testes, gera o build e publica a imagem no registry com a tag do commit. É aí que a responsabilidade da CI termina. Depois disso, o time de DevOps atualiza manualmente a tag no repositório de manifests, e esse commit é o ponto exato de entrega pro ArgoCD: a partir dali, ele detecta a mudança e aplica a nova versão no cluster.
